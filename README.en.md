# LLACC — Low Level Archive Compression Cluster

[Bahasa Indonesia](README.md) · **English**

`llacc.dll` is a .NET library for **lossless compression**. Its advantage is on **uncompressed 24-bit BMP images**. Other data can be compressed too, but with plain LZMA.

LLACC started from the idea of grouping pixels that have the same or nearly the same colour. Created by **Andi Arsal Nur**, MIT License.

## How it works

LLACC takes two strengths of LZMA, copying previously seen patterns and a continuously learning range coder, and makes them aware of the shape of an image:

| Aspect | LZMA | LLACC image model |
|---|---|---|
| Unit of data | byte | pixel |
| Copying patterns | backward distance | two-dimensional distance (rows up and columns across); the 4 latest distances are cheaper to code |
| New pixels | predicted from previous bytes | predicted from the left, upper and corner pixels |
| Images with up to 256 colours | no special handling | colour cluster table |
| Photos | no special handling | stores the difference from the prediction; green first, then used to help blue and red |
| Copy or write new | cost estimate | cost estimate using the image model |

LLACC is **not** an official version or successor of LZMA/LZMA2.

### Methods in the format

| Number | Name | When it is used |
|---|---|---|
| 0 | `Stored` | The data cannot be made smaller and is stored as is |
| 1 | `Lzma` | Plain LZMA, for anything that is not a supported image (or when LZMA is smallest) |
| 2 | `PaletteLzma` | Images with up to 256 colours: colour table + map, then LZMA |
| 3 | `Image` | LLACC image model |

The idea of "recording the positions of every colour" was also tested. It beat LZMA on only 1 of 19 images, so it is not part of the library.

## Modes

| Mode | What it does | Choose it when |
|---|---|---|
| `LlaccMode.Best` (default) | For supported BMP files: tries the image model, LZMA and the colour table (if ≤ 256 colours), then keeps the smallest | Size matters most |
| `LlaccMode.Fast` | For supported BMP files: the image model only. Otherwise: LZMA | Time and memory matter |

## Test results

19 BMP images (photos, a rendered picture, cartoons, diagrams, a chart, icons, pixel art, text pages, screenshots). Baseline: LZMA from SharpCompress 0.38.0 with a dictionary of up to 64 MB and 128 fast bytes.

| Compared with LZMA | Fast | Best |
|---|---|---|
| Images with a smaller result | 16 of 19 | 19 of 19 |
| Size difference, geometric mean | 13.6% smaller | 23.4% smaller |
| Total byte difference | 26.6% smaller | 26.9% smaller |
| Total compression time (LZMA: 73.0 s) | 31.3 s | 106.6 s |

Some examples (bytes):

| Image | LZMA | Fast | Best |
|---|---|---|---|
| Photo 1 | 949,513 | 648,538 | 648,538 |
| Photo 2 | 2,677,418 | 1,855,857 | 1,855,857 |
| Rendered picture with gradients | 1,297,986 | 925,160 | 925,160 |
| Light screenshot | 37,490 | 30,573 | 30,573 |
| Diagram without anti-aliasing | 7,277 | 5,740 | 5,119 |
| Chart, 6 colours | 5,630 | 7,399 | 3,288 |
| Pixel art, 10 colours | 10,334 | 16,181 | 6,848 |

**How to read these numbers:**

- The first eight images were already in use during development. The other eleven were created after the image model had been written. On those eleven, the advantage of Fast mode is much smaller: **6.0% smaller (geometric mean), winning on 8 of 11**. On the first eight it was 23.0%, winning on all of them.
- The photos and the rendered picture come from JPEG files shipped with Windows (some scaled down by 50%). Photos straight from a camera have not been tested. Some of the other images were generated by the test scripts.
- Times were measured once on one computer, so treat them as estimates. LZMA times were measured with the 64-bit prototype; LLACC times with the library in a 64-bit process.
- Decompressing LLACC data can be **slower** than LZMA, especially for photos.
- LLACC has **not been compared** with dedicated image formats such as lossless WebP or JPEG XL, or with 7-Zip. Do not assume it beats them.

### When LLACC does not help

JPG, PNG, GIF, MP3, MP4 and archives are already compressed and can hardly be made smaller. Audio (WAV) has no dedicated model yet and is compressed with LZMA. 8-bit, 32-bit and compressed BMP files are also compressed with LZMA.

## Usage

Add a reference to `llacc.dll`, then:

```csharp
using System;
using System.IO;
using Llacc;

class Example
{
	static void Main()
	{
		byte[] original = File.ReadAllBytes("picture.bmp");

		byte[] packed = LlaccCodec.Compress(original, LlaccMode.Best);
		LlaccInfo info = LlaccCodec.Inspect(packed);
		Console.WriteLine("{0}: {1} -> {2} bytes", info.Method, original.Length, packed.Length);

		try
		{
			byte[] restored = LlaccCodec.Decompress(packed);
			File.WriteAllBytes("restored.bmp", restored);
		}
		catch (InvalidDataException ex)
		{
			Console.WriteLine("Damaged data: " + ex.Message);
		}
	}
}
```

## API

Everything is in the static class `Llacc.LlaccCodec`. All members are thread safe.

| Member | Purpose |
|---|---|
| `Compress(byte[] data)` | Compresses in `Best` mode |
| `Compress(byte[] data, LlaccMode mode)` | Compresses in the chosen mode |
| `Compress(byte[] data, LlaccMode mode, Action<double> progress)` | Same, with progress from 0 to 1. To cancel, throw an exception (e.g. `OperationCanceledException`) from the callback; it reaches the caller |
| `Decompress(byte[] packed)` | Decompresses, with a 512 MB output limit |
| `Decompress(byte[] packed, int maxOutputSize)` | Decompresses with your own output limit |
| `CompressFile(string input, string output, LlaccMode mode)` | Compresses a file |
| `DecompressFile(string input, string output)` | Decompresses a file; the output is written only after the data is verified |
| `Inspect(byte[] packed)` | Reads the method, original size and CRC32 without decompressing |
| `IsLlacc(byte[] data)` | Checks for the LLACC signature |
| `IsSupportedImage(byte[] data)` | Checks whether the data is handled by the image model |
| `DefaultMaxOutputSize` | Default decompression limit (512 MB) |

**Errors:** damaged data, or data above the limit, throws `InvalidDataException`. A `null` argument to `Compress`, `Decompress` or `Inspect` throws `ArgumentNullException`. Running out of memory throws `OutOfMemoryException`.

When decompressing data from an untrusted source, pass a `maxOutputSize` that is only as large as you need.

## Limitations

- All data is processed **in memory**. There is no stream API. Progress reporting and cancellation exist for compression only, not yet for decompression.
- Progress is an estimate: in `Best` mode each stage has a fixed share, so its speed can feel uneven.
- The image model only handles **uncompressed 24-bit BMP**, up to 100 million pixels. Other BMP files are treated as ordinary data.
- On the 8.3 megapixel test image (24.9 MB), the prototype image-model process peaked at about **154 MB** of RAM, and its LZMA process at about 333 MB. `Best` mode also runs LZMA, so it needs at least as much as LZMA.
- In a 32-bit process the LZMA dictionary is limited to 32 MB. For data larger than 32 MB, LZMA-method results can therefore differ from a 64-bit process. Very large images can run out of memory in a 32-bit process.
- No encryption.
- CRC32 detects damage but is **not** protection against deliberate modification.
- The library is new and has **not been audited** by a third party. Keep copies of important data.

## Data format (version 1)

All numbers are little-endian.

| Offset | Length | Content |
|---|---|---|
| 0 | 4 | Signature `LLAC` |
| 4 | 1 | Format version: 1 |
| 5 | 1 | Method: 0–3 |
| 6 | 4 | Original size (int32) |
| 10 | 4 | CRC32 of the original data |
| 14 | rest | Payload, depending on the method |

- **0 `Stored`:** the original data.
- **1 `Lzma`:** 5 bytes of LZMA properties, then the LZMA stream.
- **2 `PaletteLzma`:** int32 inner length, 5 property bytes, then the LZMA stream. The inner content is: the *BMP shell*, int16 colour count, the colours (3 bytes B, G, R each), then 1 colour index byte per pixel.
- **3 `Image`:** int32 length of the compressed part, a Deflate block containing the *BMP shell*, int32 colour count (0 = full colour) and the colour table; followed by the range coder stream.

**BMP shell:** int32 width, int32 row count, int32 header length, the original header, the padding bytes of all rows, int32 tail length and the file tail. It allows the file to be rebuilt exactly.

The method 3 range coder stream depends on the details of the model: contexts, adaptation rates and bit order. The complete reference is [src/ImageCoder.cs](src/ImageCoder.cs). **Changing any model detail creates a new format**, so the version number must be increased.

`.llacc` files produced by the early prototype (signature `LLC1`) cannot be opened by this library.

LLACC builds on existing work:

- **LZ77** and **LZMA** (Igor Pavlov, LZMA SDK, public domain): pattern copying and the range coder. LLACC's range coder is a rewrite that follows how LZMA's works.
- **LOCO-I / JPEG-LS:** the median edge detector pixel predictor.
- **SharpCompress** (Adam Hathcock, MIT): LZMA engine.

Pixel contexts, colour tables and two-dimensional copying are also known in image compression. LLACC does not claim these techniques as new inventions.
